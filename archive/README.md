# archive/ — do not run anything in here

These twenty `.sql` files were the project's entire schema history. They
sat in the repository root, unnumbered and unordered, and they are kept
here because they are the only record of how the schema was built — not
because they are still usable.

**The schema now lives in `supabase/migrations/`.** That directory builds
a complete, working database from empty, in filename order, and it is
verified on every `npm run build` by `scripts/tests/db-migrations.test.mjs`.

## Why these cannot be run

**They destroy data.** Between them these files carry 124 `drop table if
exists … cascade` statements. `supabase_full_project_backup.sql` alone
has 39, covering the twelve dashboard modules, `chat_conversations`,
`chat_messages`, `user_websites`, `scheduled_agent_runs` and more. Run it
against a database with customers in it and those tables are gone —
silently, because `drop table IF EXISTS` succeeds whether or not there
was anything there.

**Order changes the result.** They are not independent. Running
`supabase_schema.sql` after `v3_instant_value_migration.sql` drops and
re-creates the module tables, discarding every column and index the V3
work had just added. That is not hypothetical: it happened while
building the replacement, and the missing columns were only caught
because the verification compares columns and not just table names.

**One of them says it is complete and is not.**
`supabase_full_project_backup.sql` describes itself as "the union of
every *.sql file in the repo root". Loaded into an empty database and
compared against the result of running every root file, it is short by
thirty-two objects — including `user_favorites`, which is the Favorites
feature: table, policies and indexes. Nine columns are missing too, among
them all six `legacy_*` columns grandfathering reads and
`free_chat_used`, which free chat reads on every message.

## What replaced them

| Migration | What it carries |
|---|---|
| `20260803000000_baseline_schema.sql` | `supabase_full_project_backup.sql` with all 39 `drop table` statements removed and every bare `create table` made `if not exists`. Same tables, columns, policies and comments otherwise. |
| `20260804000001_baseline_gaps.sql` | The thirty-two objects and nine columns the backup was missing, generated by diffing a database built from these files against one built from the baseline. Sources named per object. |
| `20260818000000_function_grants.sql` | `revoke execute` from `anon` and `authenticated`, `grant` to `service_role`, over every function in `public` — as a loop, so a function added later is covered without anybody remembering the rule. |
| `20260805…20260817` | The fourteen dated migrations that already existed, unchanged. |
| `20260817000000_drop_stale_grant_overload.sql` | Removes a duplicate `grant_credits_idempotent` that `CREATE OR REPLACE` created instead of replacing. |

## If you need something from here

Read it, take the statement you need, and put it in a **new** dated
migration under `supabase/migrations/` — idempotent, and with no `drop
table`, no `truncate` and no unqualified `delete`. The build gate will
tell you if the object you added is missing from the migration path.

## Reproducing the database from scratch

```sh
createdb ionexa_local
psql -q -d ionexa_local -f scripts/db/bootstrap-supabase.sql   # what Supabase provides: auth/storage schemas, roles, extensions
for f in supabase/migrations/*.sql; do psql -q -v ON_ERROR_STOP=1 -d ionexa_local -f "$f"; done
DATABASE_URL=postgres://…/ionexa_local node scripts/tests/db-migrations.test.mjs
DATABASE_URL=postgres://…/ionexa_local node scripts/tests/credit-flow.dbtest.mjs
```

`scripts/db/bootstrap-supabase.sql` is **not** part of the project's
schema. It stands in for the pieces a hosted Supabase project provides
before any project migration runs — `auth.users`, `auth.uid()`,
`storage.objects`, the `anon` / `authenticated` / `service_role` roles,
and the three extensions. Against a real Supabase database you skip it.
