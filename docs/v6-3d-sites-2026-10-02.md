# 3D websites: what it takes, what it costs, and one sample

Queue item 1 of 6. Analysis plus one sample; the full feature is not built.

    node scripts/sample-3d.mjs     # serves the sample, opens it eight ways, prints the costs

The sample is `docs/samples/3d-site/`: `page.src.html` is what the model would
write, `ionexa-3d.js` is what we would write once. Every number below was
printed by that command on 2026-10-02 unless it says otherwise.

## The answer in four lines

1. **Today the product cannot ship a 3D site, however well the model writes
   one.** The builder's prompt forbids `<script>` beyond two narrow cases, and
   `stripDisallowedExternalScripts` removes every `<script src>` at generate,
   edit, publish and rollback. Three.js from a CDN would be stripped silently.
2. **3D costs almost nothing to generate.** On the sample it adds 1,835
   characters — 459 output tokens, **about 2 credits on Growth** — to what the
   model writes. Not 8-10x. What makes a site 10x is length and page count, and
   that is already measured and already charged (26 vs 264 credits, recorded in
   `src/lib/billing/estimate.ts`).
3. **It costs the visitor 216 KB** (gzip): 211 KB of libraries and 5 KB for
   the component. A plain site costs them nothing extra.
4. **It never goes blank.** Eight scenarios, all pass: the 3D appears where a
   device can carry it, and otherwise the page is the same page with a drawing
   where the scene would be.

## α. Feasibility: the obstacle is the security rule, not the model

| what | where | today |
|---|---|---|
| the prompt | `src/lib/website-builder.ts`, the ANIMATIONS and output rules | "No `<script>` tags EXCEPT" scroll-reveal and the contact form |
| the scanner | `stripDisallowedExternalScripts` in `src/lib/website-html-security-scan.ts` | removes **every** `<script src>`, not only off-site ones |
| where it runs | `api/websites/generate/process`, `api/websites/edit`, `api/websites/[id]/publish`, `api/published/[id]/rollback` | four places, one function |

`node scripts/sample-3d.mjs` runs that real function over the sample — the
`todays-scanner` row below. The page survives it, readable, as a plain site:
no 3D, nothing broken.

### The recommendation: the model writes no JavaScript at all

Two ways to build the 3D level:

| | the model writes Three.js | the model writes attributes, we write the JS once |
|---|---|---|
| what changes in security | allow arbitrary model-written scripts | allow **exactly** our pinned same-origin files |
| per-site reliability | a new WebGL program per site, each a fresh way to show a blank hero | one program, tested once (the eight scenarios) |
| extra output per site | ~12,400 characters, ~13 credits on Growth | ~1,800 characters, ~2 credits |
| moat | the same | the same |

The second is what the sample does. The page asks for motion with
attributes — `data-ionexa-3d="bowl" data-color="#b4532d"`, `data-reveal`,
`data-parallax="0.12"` — and `ionexa-3d.js` does the rest. **The decision that
needs you** is the security change: `stripDisallowedExternalScripts` keeps
stripping everything except the five pinned paths under one directory we
serve ourselves.

## β. UMD builds: possible, and frozen at a version from 2023

Measured against the npm registry on 2026-10-02:

| library | UMD build | gzip |
|---|---|---|
| three | `build/three.min.js` exists up to **0.160.0**; 0.161.0 dropped it; newest is 0.186.1 | 166 KB |
| gsap | `dist/gsap.min.js` 3.12.5 | 28 KB |
| ScrollTrigger | `dist/ScrollTrigger.min.js` 3.12.5 | 18 KB |
| lenis | `dist/lenis.min.js` 1.1.13 | 4 KB |

UMD means pinning Three to 0.160.0. Everything a site needs (geometry,
lights, physical materials) is there. The alternative is ES modules with an
import map, which is the "imports that break" you asked to avoid.

cdnjs and jsdelivr answered **403** to this environment (its network policy),
so the sample was tested with the same files from npm. That is also the
argument for serving them ourselves: a site that loads its 3D from a third
party fails when that party does.

## γ. Mobile and the three tiers

Decided before anything is drawn (`decide()` in `ionexa-3d.js`):

| tier | when | what runs |
|---|---|---|
| full | desktop, WebGL, 5+ cores and 5+ GB | scene, steam, pointer tilt, smooth scroll, parallax |
| lite | a phone, or a weak machine | the scene at 1x pixels; native scroll; no steam |
| static | no WebGL, reduced motion, Save-Data, a weak phone, libraries missing | the drawing that is already in the HTML |

Nothing in the CSS starts invisible. The page reads before the script runs,
and stays readable if it never runs.

### The eight scenarios

| scenario | tier, and why | first frame* | canvas drawn | result |
|---|---|---|---|---|
| desktop | full, capable | ~1.5 s | 100% | ok |
| phone 390 px | lite, small screen | ~0.6 s | 100% | ok |
| weak phone (4 cores, 2 GB) | static, weak phone | — | — | ok |
| no WebGL | static, no-webgl | — | — | ok |
| reduced motion | static, reduced-motion | — | — | ok |
| libraries blocked | static, libs-missing | — | — | ok |
| today's scanner | no script runs | — | — | ok |
| JavaScript off | — | — | — | ok |

\* A local server and software WebGL: these show the order of the work, not a
real-world load time. Real-device timing has not been measured.

Every row requires the business's facts to be readable (name, a dish, a
price, the address, the hours), all 12 dishes in the DOM, no script errors, no
sideways scroll, Commissioner actually loaded, and either a scene with a drawn
centre or the drawing — never neither.

### Three checks that exist because the first run passed without them

- **The scene never started**, and two scenarios passed the tier check: the
  component read `host.dataset.ionexa3d`, but `data-ionexa-3d` does not
  camel-case — a dash before a digit is left alone. The scenario now requires
  a drawn frame and a drawn canvas centre.
- **The headings were in a fallback face.** The test's font CSS used a
  relative `url()`, which resolved against Google's host. The run now asks
  `document.fonts.check`; with the relative path back, 7 of 8 scenarios fail.
- **innerText counts invisible text.** "Readable" could not see a section that
  rose in on scroll and never arrived. The run now scrolls the whole page and
  requires every revealed block to be fully visible; with the trigger made
  unreachable, it fails with "14 revealed block(s) still invisible".

## δ. SEO

The 3D is an enhancement over a normal page, not the page itself. With
JavaScript off, the `no-javascript` row has the title, the description, the
heading, all 12 dishes with prices, the address and the hours. A crawler gets
what a plain site gives it.

Not measured: Lighthouse, Core Web Vitals on a real device. The 216 KB is the
known cost; whether it moves a ranking is not.

## ε. The moat holds, at no extra cost

Everything a visitor reads in the sample is the business's own record: the
menu, the prices, the street, the hours. The scene takes its colours from the
brand (`data-color`, `data-accent`, `data-glaze`) and its object from what the
business is (a bowl, for food). In the product those come from the same
`buildBusinessContextBlock` that a plain site already gets, because the
context sits upstream of whatever the model is asked to write.

Framer does 3D and does not know your menu. This does both, and the knowing
is free: it is the same context block either way.

## The pricing question this changes

You set the rule that credits follow real cost times the margin. Measured,
3D adds about 2 credits on Growth. So:

- **priced on cost**, the 3D level is the site's price plus about 2 credits
  — roughly 1.05x, nowhere near 8-10x;
- **priced at 8-10x**, it is priced on value, and that is a legitimate choice
  — but it breaks the "credits = cost x margin" rule for this one feature, and
  should be written down as an exception rather than discovered later as a
  margin of 50x.

The same holds for the tier gate. "3D on Growth and above" is a product
decision about who gets the premium experience. The cost does not force it.

**Premium** (reveals, parallax, smooth scroll, no WebGL) is the same page
with `data-reveal` and `data-parallax` and three of the four libraries,
about 50 KB. Its generation cost was not measured separately. It is bounded
above by the 3D figure, because it is a subset of the same attributes.

## Not measured, and what it would take

| question | why not here | what answers it |
|---|---|---|
| does the **model** reliably write the attribute vocabulary | `ANTHROPIC_API_KEY` is 0 characters in this environment | one real generation per level, about EUR 1.50 in total |
| real-device load and frame rate | no device | a phone and a Lighthouse run after the first real site |
| scenes beyond the bowl | one sample was asked for | a short list (cup, box, shape...) is a list in one file, not a rewrite |

## What "the full feature" would be, in order

1. **Your decision on the scanner**: allow the five pinned same-origin paths, nothing else.
2. Serve the pinned files ourselves, beside the app.
3. A level switch in the builder (simple default, premium, 3D) that changes
   the prompt's attribute vocabulary and the script tags it may emit.
4. An estimate per level, shown before generation, from the measured figures.
5. The tier gate, if you keep it.
6. The gates you asked for: 3D as default goes red; a 3D page without the
   static drawing goes red; a 3D generation without a cost shown first goes
   red.
7. One real generation per level, with a key, to measure reliability.
