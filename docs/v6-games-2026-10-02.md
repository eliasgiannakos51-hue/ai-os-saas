# Games — what it would mean here, who would pay, and whether it is worth it

Analysis only, written 2026-10-02. Nothing was built. Every figure is tagged
the way `docs/v6-analysis-2026-10-02.md` tags them: **MEASURED** (a command
in this repo, named beside it), **LOOKED UP** (with the date), **DERIVED**
(arithmetic over the two, inputs shown), or a dash.

## 1. Three different products share the word

| | what the person says | what comes out | who asks |
|---|---|---|---|
| **A. Quiz / interactive page** | "ένα κουίζ «ποιος καφές σου ταιριάζει» για το Instagram μου" | one page, 5–8 questions, a result, an optional "leave your email" | a café, a shop, a gym — the people this product already sells to |
| **B. Training quiz from their own material** | "κάνε τεστ για τους νέους υπαλλήλους από το εγχειρίδιό μου" | questions generated from files they uploaded, scored | a business with staff; a teacher; a creator selling a course |
| **C. An arcade game** | "φτιάξε ένα παιχνίδι σαν το Flappy Bird" | a canvas game with a loop, physics, a score | consumers, children, hobbyists — nobody on the current pricing page |

They are not three sizes of one feature. A and B are **business tools that
happen to be interactive**; C is entertainment.

## 2. What the code allows today

**MEASURED 2026-10-02**, by reading the files named:

- **The builder may not write JavaScript.** `src/lib/website-builder.ts`
  line 620: *"No `<script>` tags EXCEPT the two specific, narrow exceptions"*
  — scroll-reveal and the contact form. A quiz needs state (which answer,
  which result); a game needs a loop. Neither fits either exception.
- **The scanner would let inline JavaScript through.**
  `src/lib/website-html-security-scan.ts` strips every `<script src>` and
  flags `eval` / `new Function`, but an inline `<script>` block is not
  flagged at all — only inline event *handlers* are inspected for `fetch`,
  cookies or storage.
- **The preview cannot run it.** Every preview iframe in
  `src/components/website-builder/website-builder-workspace.tsx` is
  `sandbox=""`, which runs no script. A person could not play their game
  before publishing it.
- **The published page can run it.** `src/lib/publishing/public-serving.ts`
  sends `script-src 'self' 'unsafe-inline'`.
- **A quiz's lead capture already exists.** Forms post to the app's own
  `/api/websites/[id]/submit-form`, which stores the submission. Option A's
  "leave your email" needs no new backend.
- **Option B has a field and nothing behind it.** `src/lib/modules.ts`
  gives the learning module a `quiz` textarea — free text, not a generated,
  scored quiz.

## 3. The obstacle is not the generator. It is where the page is served.

**MEASURED 2026-10-02:** a published site is served at `{origin}/s/{subdomain}`
— `src/app/s/[subdomain]/route.ts` — which is **the same origin as the
signed-in app**. Its CSP allows inline script, `connect-src 'self'` lets that
script call `/api/*`, and `img-src https:` lets it send anything to any host
as an image URL. The browser client (`src/lib/supabase/client.ts`,
`createBrowserClient`) reads the session from `document.cookie`, so the
session cookie is readable by script on that origin.

What keeps that safe today is one thing: **the model is told not to write
script**, and a second reviewer (`src/lib/website-security-review.ts`)
reads the first 12,000 characters of the page for phishing-shaped content —
not for script behaviour, and not past 12,000 characters, which is where a
`<script>` before `</body>` sits on a long page.

**This is already a risk, without games.** A prompt is not a security
boundary: someone who can talk the generator into one script block could
publish a page that acts as any signed-in Ionexa user who opens it. Not
reproduced — it needs a live generation and a second account — so it is
written here as a finding to verify, not as a demonstrated exploit.

**A games feature turns that from an exception into the norm.** The moment
the builder is *asked* for JavaScript, "the model will not write a script"
stops being true by design. So whichever option is chosen, this comes first:

1. serve published pages **from a different origin** — a separate domain,
   or the CSP `sandbox allow-scripts allow-forms allow-popups` directive,
   which gives the page an opaque origin with no access to the app's
   cookies;
2. then the form endpoint must accept that origin explicitly (CORS on
   `submit-form` only);
3. then the preview can be `sandbox="allow-scripts"` — still without
   `allow-same-origin` — so a quiz can be tried before it is published.

Item 1 is worth doing on its own merits. It is a security change, so it is
listed here and not done in an analysis round.

## 5. Who would pay, and is it worth it

| option | buyer exists? | moat | effort before it is safe | verdict |
|---|---|---|---|---|
| **A. quiz / interactive page** | yes — the same café that buys the website | weak: many quiz makers exist; strong only if results flow into the CRM-shaped records this product already keeps | §3 first, then a prompt branch and a preview change | **yes, after §3** |
| **B. training quiz from own files** | yes — businesses with staff, creators with courses | **strong**: generated from the person's own uploaded material, which no general tool has | §3 is not needed if the quiz is played INSIDE the app; scoring and storage are new | **yes — the best of the three** |
| **C. arcade game** | **0 identified** | none — every general model does it | §3, plus a playable preview, plus a different customer | **no** |

**My recommendation, in order:**

1. **Fix where published pages are served (§3)** — it is a risk today,
   whatever you decide about games.
2. **B: quizzes from the person's own files**, played inside the app. It
   uses what makes Ionexa different (their data), needs no published
   JavaScript, and has an obvious buyer.
3. **A: the marketing quiz**, as a website section once §3 is done.
4. **C: not at all.** Not because it is hard — it is the easiest of the
   three to demo — but because nobody this product sells to asked for it.
